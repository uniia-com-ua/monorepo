## Робота з GitHub (мінімум бюрократії)

Мета — зберегти фокус і мотивацію. Тримаймо процес простим: одна задача → одна гілка → один PR.

### Коротко про процес
1) Створити Issue. 2) Від нього — гілку. 3) Зробити PR і змерджити після одного апруву.

---

## 1) Issue (задача)
- Створюємо для будь-якої зміни, що займає >10–15 хв.
- Назва: коротка у наказовій формі ("Add dark mode toggle").
- Одна людина — одна Issue.

Шаблон опису (за бажанням, можна стисло):

```md
Context: чому це потрібно / посилання
Done: очікуваний результат у 1–2 реченнях
Checklist:
- [ ] ключовий крок 1
- [ ] ключовий крок 2
Screenshots/Links: за потреби
```

---

## 2) Гілка (branch)
Формат назви:

```
(тип)/(номер-issue)-(короткий-опис)
```

Типи (мінімальний набір):

| Тип       | Коли використовувати                                |
| --------- | ---------------------------------------------------- |
| `feat`    | новий або помітний функціонал                        |
| `fix`     | виправлення багу                                     |
| `chore`   | рутина: оновлення залежностей, конфіг, дрібні правки |
| `refactor`| переробка без зміни поведінки                        |

Приклади:
- `feat/42-settings-add-user`
- `fix/128-drawer-overflow`

---

## 3) Коміти
Формат повідомлення:

```
(тип): #<номер-issue> <опис у наказовій формі>
```

Приклад: `feat: #42 implement UsersTable for settings page`

Поради:
- 1–3 комітів на PR достатньо.
- Пишемо лаконічно; імена компонентів з великої: `UsersTable`.

---

## 4) Pull Request (PR)
- Назва PR = назва Issue.
- В описі достатньо зазначити, що закриває задачу, і 2–5 пунктів, що зроблено.

Шаблон опису PR:

```md
Closes #<номер>

Що зроблено:
- пункт 1
- пункт 2

Скріншоти/відео: (за потреби)
Як протестувати: короткі кроки (за потреби)
```

Чекліст перед злиттям:
- [ ] локально відкривається і немає помилок у консолі
- [ ] не ламає інші сторінки (базовий клік-тест)

---

## 5) Рев'ю та злиття
- Будьмо доброзичливі; максимум 3 блокуючі коментарі на PR.
- Пропонуємо правки через inline suggestions.
- Мердж: "Squash and merge" після 1 апруву. Якщо PR дрібний і очевидний — дозволено self-merge після короткого очікування, якщо ніхто не проти.

## 6) Принципи мінімального тертя
- Маленькі PR-и легше оглядати (орієнтир: до ~300 змінених рядків).
- Краще відкрити PR раніше як Draft, ніж "зависнути" надовго.
- Не перфекціонізм: робимо корисний мінімум і рухаємося далі.

---

Дотримання одного стилю назв гілок/комітів/PR і вказування номера Issue допоможе автоматично збирати історію змін у задачі та зекономить час усім.
